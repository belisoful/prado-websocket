# Audit — 2026-11-03

Scope: the whole extension at `69c38bd` (`src/`, `examples/chat`, `prado-pubsub.js`, tests, CI,
packaging, docs) against PRADO `master` at `b079b8d14` and `belisoful/prado-http2` 1.3.0.
This is the first audit since [AUDIT_2026-09-22.md](AUDIT_2026-09-22.md) and covers the work since:
the `prado.pubsub.v1` subprotocol and browser client (never reviewed before), the chat example,
the move onto PRADO's event loop API (`8a59110`), and the HTTP/2 busy-session input hold (`b264fb1`).

Method: five independent reviews (protocol layer; server and runtime; cluster; pub/sub and the
chat example; tests, CI, packaging and docs), each told to confirm high and medium findings with
a probe script against real classes, real socket pairs or `127.0.0.1:0` listeners. Every high
finding below, and the medium findings marked *confirmed*, was re-run by hand afterwards and
reproduced. The probes live in the session scratchpad, not the repo; each finding gives enough to
rebuild one as a regression test.

Baseline: `php -l`, php-cs-fixer, phpstan level 3 and the unit suite (495 tests) pass on PHP 8.2,
8.4 and 8.5. None of the findings below is caught by the suite.

Severity: **high** = security bypass, process crash, unbounded resource use, a hang, a permanent
fault, or silent data loss; **medium** = a robustness or interop defect reachable by a conforming
or buggy peer or by ordinary application code; **low** = spec nit, docblock, hygiene.

## 1. Summary

| Area | High | Medium | Low |
|---|---|---|---|
| Server and runtime (incl. HTTP/2) | 5 | 6 | 6 |
| Protocol layer | 2 | 5 | 4 |
| Cluster | 5 | 6 | 4 |

The themes:

1. **HTTP/2 escapes the limits HTTP/1.1 enforces.** Handshake and idle timeouts, `CloseTimeout`,
   `MaxConnections` per stream, `MaxSendBufferBytes`, and the guarded teardown fixed for HTTP/1.1 in
   September (prior findings 1–3, 11, 12, 15) never reached the HTTP/2 path. The README says they
   apply to both.
2. **Presence is not convergent across nodes.** Every backplane can leave other nodes with
   permanent phantom clients after a crash, a restart under a static `NodeId`, a stall, or an
   outage. Prior finding 7 was fixed for the reaping node only.
3. **Untrusted input reaches unbounded work.** A frame trickled in small pieces costs quadratic
   time; bytes after a Close are buffered without limit; pub/sub `json_decode()` of a 10 MiB frame
   takes ~600 MiB and kills the daemon.
4. **PRADO's error handler turns stream notices into `TPhpErrorException`**, which the
   `catch (\RuntimeException)` blocks around `fwrite`/`fread` do not catch, so the documented
   `websocket_write_failed` path and its state reset never run.

Recommended fix order: §2 items H1–H3 (security), then H4–H8 (DoS and limits), then the
presence convergence group (H10–H13), then the mediums.

## 2. High

### H1. Messages are dispatched after the server or application has closed the connection — authentication bypass
*Confirmed.* `TWebSocketServer.php:1574-1576` (HTTP/1.1) hands every decoded message to
`onMessage()` without checking `getIsClosing()`; `TWebSocketConnection::feedMessages()` keeps
returning data messages until the peer's Close arrives. The documented pattern (README:284,
`TWebSocketPubSubHandler` docblock) is to authenticate in `onOpen` and close with 4401/4403.
A client that pipelines requests behind its handshake, or ignores the Close, keeps being served
until `CloseTimeout` (5 s): in the probe `onCall`, `onSubscribe` and `onPublish` all ran for a
client `onOpen` had closed. Replies are suppressed but side effects (calls, publishes, sends to
other clients) happen. The defect is server-wide, not pub/sub specific; check the HTTP/2 stream
path too. Fix: drop data messages once the connection is closing (server dispatch, both paths),
and add a regression test with a pipelined request.

### H2. A node without the mesh secret can join through a second node used as a signing oracle
*Confirmed.* `Cluster/TMeshBackplane.php:437-450` (`answerChallenge`), `:462-481`
(`verifyChallenge`), `:553-561` (`authenticate`). The handshake proof is a bearer token over a
client-chosen `Sec-WebSocket-Key` (the docblock says it can be replayed), and a node answers
`AUTH_CHALLENGE` from a peer it has not verified. With one captured plaintext handshake, an
attacker links to A and B, sends B's nonce to A as a challenge, and hands A's answer to B under
origin `A`. B verifies the attacker as "A", sends it B's presence (client ids and metadata) and
all cluster traffic, and A accepts forged `PRESENCE_SET` the same way. This is broader than the
prior "relay through a node holding the secret" note: only honest nodes are needed. The class
docblock (`:46-51`) claims a captured handshake cannot be replayed onto the mesh. Fix: the
accepting side answers no challenge until it has verified the dialer (the dialer answers first).

### H3. Pub/sub decodes up to `MaxMessageSize` of JSON before any check — one frame kills the daemon
*Confirmed.* `PubSub/TWebSocketPubSubHandler.php:187`. Every admitted text frame is
`json_decode()`d at up to 10 MiB before the type check or any application hook; `MAX_JSON_DEPTH`
does not bound memory. A 10 MiB `{"type":"x","pad":[[1],[1],…]}` adds ~604 MiB of heap; at a
256 MiB `memory_limit` the process dies with every connection on it. With H1 it needs no
authentication. Fix: a handler-level frame byte cap (e.g. 64 KiB, configurable) before decoding,
and document a small `MaxMessageSize` for pub/sub servers.

### H4. One reset peer at capacity leaks a transport and inflates the load permanently
*Confirmed.* `TWebSocketServer.php:1069-1075`. When `MaxConnections` is reached the shed path
writes the 503 and then closes; when the write throws (peer reset), `close()` is skipped,
`readyListener()` (`:680`) only logs, and the transport stays in the registry. With
`MaxConnections=1` and one client, 20 reset-on-connect peers raise `getLoad()` to 21; after the
client leaves it stays at 20 and every new client gets 503 forever, with the fds leaked. Fix:
close in `finally`.

### H5. HTTP/2 escapes `HandshakeTimeout`, `IdleTimeout` and `CloseTimeout` (slowloris)
*Confirmed.* `pumpHandshake()` `:1147-1153`, `selectHttp2()` `:1196-1198`,
`acceptHttp2Session()` `:1332`, `reapIdleSessions()` `:978-980`. Four bytes `PRI ` select HTTP/2,
which forgets the pending session and its deadline; the HTTP/2 session has no deadline and no
activity stamp, and the idle reaper skips it on the stated grounds that nghttp2 PINGs keep it
alive — nothing sends PINGs. With both timeouts at 0.3 s, a `GET ` peer is dropped and `PRI ` and
full-preface peers are still connected after 2 s and never reaped. ALPN `h2` behaves the same.
README:232 says these limits apply on both paths.

### H6. `MaxConnections` is not enforced per HTTP/2 stream
*Confirmed* (still open from the prior audit). `THttp2WebSocketProtocol.php:105` submits only
`ENABLE_CONNECT_PROTOCOL` (no `SETTINGS_MAX_CONCURRENT_STREAMS`) and `acceptStream()` `:363-420`
has no cap. With `MaxConnections=2`, one transport opening 500 CONNECT streams gets 500 `onOpen`
calls and a load of 501, each with a connection, a cluster registration and handler state.

### H7. `MaxSendBufferBytes` has no effect on HTTP/2
*Confirmed.* `THttp2WebSocketProtocol.php:401` drains each connection's `_outbound` into the
`TH2Stream`'s own buffer, which accepts everything; the session-level `outbound` string
(`TWebSocketServer.php:1488-1526`) is uncapped too. A peer advertising
`SETTINGS_INITIAL_WINDOW_SIZE=0` lets the server queue 17.2 MiB on one stream at a 1 MiB limit
with no exception. Broadcasts or pub/sub to such a client grow memory without bound.

### H8. A frame fed in small pieces costs quadratic time
*Confirmed.* `TWebSocketConnection.php:513` (`$buffer = $this->_readBuffer . $bytes`) and the
`tryDecode(substr(...))` on the incomplete tail copy the whole buffered frame on every read.
64 KiB fed in 64-byte pieces took 1.9 s; a 10 MiB frame near `MaxMessageSize` trickled at
~64 KB/s saturates the single-threaded reactor, and the idle reaper never fires because bytes
keep arriving. The same path serves HTTP/2 streams and mesh links. Fix: append in place and
remember the pending frame's total length so an incomplete feed returns without copying or
re-parsing.

### H9. Bytes after the peer's Close are buffered without limit
*Confirmed.* `TWebSocketConnection.php:519/544`. Once `_closed` is set the decode loop is skipped
but the `finally` keeps the whole buffer. A peer that stops reading (so the echoed Close stays
queued and the session lives on), sends Close, then streams junk grows `_readBuffer` until
`CloseTimeout` × link rate — unbounded with `CloseTimeout=0`. The probe exhausted a 128 MiB
`memory_limit`. Fix: discard input once closed.

### H10. Mesh link output that the kernel does not take at once is never flushed by the loop
*Confirmed.* `Cluster/TMeshBackplane.php:740-749` (`sendTo()`); the server registers cluster
sources readable-only (`TWebSocketServer.php:740-760`) and `armWrites()` (`:768-778`) covers client
sessions only. A 2 MiB broadcast stayed queued after 200 ticks; one heartbeat (TTL/3) drained
~8 KB. Large messages stall for minutes, and steady traffic grows the queue to the overflow
limit, which drops the peer and the queued envelopes.

### H11. A Redis node stalled past `NodeTtl` is reaped and stays deaf after it resumes
*Confirmed.* `Cluster/TRedisBackplane.php:469-482`: `heartbeat()` re-adds the node to `nodes`,
but the rebuild (`resync`) runs only from `open()` (`:143-146`), and `reapNode()` (`:514-535`)
already removed its channel interest and presence. After a GC pause or VM suspend the node is
listed alive but receives no channel traffic and its clients are unreachable by `sendToClient()`.
Fix: rebuild when the node finds its own entry was reaped (`sAdd` returns 1, or `node:{self}` is
missing).

### H12. Crash reaping clears only the reaping node's mirror (Redis and File)
*Confirmed.* Prior finding 7 is fixed for one node only. Redis: `:497-501`, `:536-539` — the first
node to prune removes the dead node from `nodes` and drops presence locally; every other node no
longer sees the dead node and never drops its clients. File: `TFileBackplane.php:281-290` — the
reaper unlinks the file and drops locally; other nodes no longer find it. With A, B, C and C
crashing, B keeps C's clients forever; the phantoms accumulate across crashes. Fix: the reaper
publishes a node-down (the reserved, unused `NODE_DOWN`) that every receiver applies.

### H13. Phantom presence after a restart under a static `NodeId`, or a departure during an outage
*Confirmed.* Redis restart: `open()` (`:143`) purges the old incarnation's hash entries but never
tells peers, and the id never expires, so peers keep the old clients (still present after
1000 s in the probe). Redis outage: an `unregister` during the outage is a guarded no-op
(`:387-393`) and `resync()` (`:287-301`) re-sets only current clients, so peers never get the
drop; `testUnregisterDuringAnOutageDoesNotLeaveAPhantomAfterReconnect` checks only the hash.
Mesh: join state (`:414-423`) only adds, so a restarted node's previous clients stay on peers.
Same root cause as H12: there is no "replace this node's presence" step. A per-incarnation epoch
or a `NODE_DOWN` before re-announcing fixes both. `TRedisBackplane.php:40-42` claims nothing
declared during an outage is lost.

## 3. Medium

### Server and runtime
- **M1. A throwing `onClose` on HTTP/2 leaves cluster presence for every stream on the transport.**
  *Confirmed.* `THttp2WebSocketProtocol.php:466-476`, `:499-511`: the handler's `onClose` runs
  unguarded before the server's unregister, and in `shutdown()` the first throw aborts the loop.
  Three streams, throwing `onClose`: load 0, cluster local clients 3. Prior finding 11 was applied
  to HTTP/1.1 only.
- **M2. A handler exception on one HTTP/2 stream kills every WebSocket on that connection.**
  *Confirmed.* `TWebSocketServer.php:1629-1642` catches only `THttp2Exception|TWebSocketException`
  from `receive()`, so a `RuntimeException` from tab A's `onMessage` closes tab B too, with no
  `onError`. HTTP/1.1 (`:1574-1576`) drops the connection with no Close frame (peer sees 1006), no
  `onError`, and loses the rest of the batch; the synchronous path sends 1011 and raises `onError`.
- **M3. Shutdown is not graceful.** *Confirmed.* `serve()` `:618-636` never closes live sessions:
  no Close 1001, no `onClose`. Standalone, the fds leak; under the module the transports are closed
  but `onClose` never runs, so application state tied to it leaks on every deploy.
- **M4. A throwing loop callback ends `serve()`.** `serve()` installs no error handler on the
  reactor, which is the `TAsync` loop since `8a59110`; an uncaught throw from an application
  `delay()`/`repeat()` callback or a resumed fiber exits the daemon (leaving connections as in M3).
  Revolt behaves the same by default, but nothing documents it.
- **M5. A handler waiting on the main fiber lets HTTP/1.1 messages reorder and arrive after
  `onClose`.** *Confirmed.* `handleHttp1Bytes()` `:1556-1578`, `readySession()` `:690-701`. A
  `TAsync::sleep()` in `onMessage` ticks the reactor, which reads and dispatches the same session
  re-entrantly: `msg:1 | msg:3 | onClose | msg:1 done | msg:2`. `b264fb1` guards HTTP/2 only.
  A second nested wait throws from `TLoopSuspension` and drops an unrelated session; during such a
  wait `tickCluster()` (`:722-733`) no-ops after its first run, so a readable cluster source spins
  at 100% CPU.
- **M6. Stream notices escape as `TPhpErrorException`.** *Confirmed.* PRADO's error handler turns
  `fwrite`/`fread` EPIPE/ECONNRESET notices into `TPhpErrorException`, not `\RuntimeException`, so
  `TWebSocketConnection::flushOutbound()` (`:271`), `readTransport()` (`:1420`) and
  `drainHttp2Output()` (`:1520`) miss them. `send()` to a reset peer throws the wrong type, the
  documented `websocket_write_failed` never appears, `_outbound` keeps growing (102 → 204 bytes
  over two sends) and `getIsClosed()` stays false. The server's outer `catch (\Throwable)` contains
  it. Fix: catch `\Exception` (or `TPhpErrorException` too) at those sites.

### Protocol layer
- **M7. `HandshakeTimeout` does not bound a silent peer on a blocking stream.** *Confirmed.*
  `TWebSocketHandshake.php:562`: the deadline is checked between blocking `read(1)` calls and the
  stream timeout is never set to the time remaining. With 0.5 s, a peer sending one line blocked
  for `default_socket_timeout` and then threw `RuntimeException`, which escapes
  `serveConnection()`'s `catch (TWebSocketException)`.
- **M8. A partial frame on a non-blocking stream throws and loses its bytes.** *Confirmed.*
  `TWebSocketFrameCodec.php:337-339` via `receiveFrame()` (`:445`). The docs promise `null` when
  no frame is available yet; with 3 of 17 bytes arrived, `receive()` throws
  `websocket_frame_incomplete` having consumed them, and the next call misparses the rest.
  `drainClose()` swallows it and reports a close without the peer's Close.
- **M9. A blocking read timeout is treated as fatal on the synchronous path.**
  `TWebSocketFrameCodec.php:357`: a client idle beyond `default_socket_timeout` makes `receive()`
  throw `RuntimeException`; the handler trait fails the connection with 1011. That path has no
  keepalive, so ordinary idle clients are dropped.
- **M10. The server omits `server_max_window_bits` when the client offered 15.** *Confirmed.*
  `TPermessageDeflateNegotiator.php:165` echoes it only below 15; RFC 7692 §7.1.2.1 says a server
  accepts the parameter by including it. A strict client fails the handshake.
- **M11. `feedMessages()` discards a read's decoded messages when a later frame is malformed**
  (still open from the prior audit): `$messages` is local, so the exception loses them.

### Cluster
- **M12. File backplane: the refresh `touch()` recreates an empty presence file after a peer
  reaped it.** *Confirmed.* `TFileBackplane.php:263-265`. A resumed node's live client is
  invisible to the reaper and to late joiners (`seedPresence()` skips 0-byte files).
- **M13. File reaper sends the URL-encoded client id.** *Confirmed.* `TFileBackplane.php:284` uses
  `basename()`, `seedPresence()` (`:404`) uses `rawurldecode()`. With a `NodeId` such as `host:q`
  the drop names `host%3Aq-…` and the mirror entry is never removed.
- **M14. A `tls://` mesh dial blocks the event loop** (prior item 16, mesh part, still open).
  `TMeshBackplane.php:526`: `stream_socket_client()` runs the TLS handshake synchronously even
  with `ASYNC_CONNECT`; a peer that stalls TLS blocked the loop 2 s per attempt, repeated every
  heartbeat for a gossiped URI. Hostnames also resolve synchronously. Contradicts `:43-44`.
- **M15. The accepting end of a mesh link inherits the client `MaxMessageSize`.** *Confirmed.*
  `TWebSocketServer.php:1250`: with `MaxMessageSize=1000`, a client-legal 900-byte binary
  broadcast exceeds the limit once base64-encoded in an envelope and drops the peer. With
  defaults, any binary payload over ~7.5 MiB kills every link. The dialing side uses 10 MiB.
- **M16. In a partial mesh, presence behind an intermediary is lost for good after a transient
  silence.** *Confirmed.* `TMeshBackplane.php:273-292` drops it; re-link join state
  (`:414-423`) carries only the direct peer's clients.
- **M17. Redis and File are poll-only with a capped drain** (from reading). An idle node ticks the
  cluster about once a second, and Redis drains at most 1000 envelopes per tick; sustained churn
  past that fills the inbox to `InboxLimit`, which trims the oldest entries, presence drops
  included.

### Pub/sub, JS client, chat example
- **M18. Each disconnect costs time proportional to all channels on the node.** *Confirmed.*
  `TWebSocketCluster.php:153` scans every channel on `unregister()`. 3000 clients × 64
  subscriptions: ~47 ms per disconnect, so a mass disconnect stalls the loop for minutes. Fix: a
  per-client channel index.
- **M19. An application-thrown `TWebSocketException` drops the requester's session.**
  *Confirmed.* `TWebSocketPubSubHandler.php:206-207` rethrows every `TWebSocketException` from
  dispatch as a transport failure — including one from an `onCall` handler, or a send to another
  client whose buffer overflowed. The requester gets no `internal` reply and loses its session
  (over HTTP/2, the whole connection). Rethrow only failures of the requester's own reply writes.
- **M20. Payloads are not relayed faithfully.** *Confirmed.* `json_decode(..., true)` at `:187`:
  `{"data":{}}` republishes as `[]`, `{"0":"x","1":"y"}` as `["x","y"]`, integers past 2^63 lose
  precision, and `1e400` becomes INF so the reply is `internal` and an ERROR is logged per request.
- **M21. An undecodable frame loses its id, so the JS request hangs until timeout.** *Confirmed.*
  `:187-190`: a lone UTF-16 surrogate (JS string truncation of an emoji) or nesting past the depth
  limit gets an id-less `bad_request`; the `prado-pubsub.js` promise waits the full
  `requestTimeout` and a stray `error` event fires. Recover the id with a cheap pre-scan, or
  document it.
- **M22. JS: one unserializable payload poisons the offline queue.** *Confirmed with node.*
  `prado-pubsub.js:220-222`, `:331`: a BigInt or cyclic payload queued offline throws in
  `onopen`; the queue was already reset, so every later queued frame is lost and their promises
  never settle. Online, the promise rejects but its `_pending` entry leaks (`:320-323`).
- **M23. Chat example memory grows without bound.** *Confirmed.* `ChatHandler.php:119-125`,
  `:214-216`: history and sequence maps are never pruned when a room empties and room names are
  unlimited; one client left 99.7 MiB retained. Example code, but it is the reference app.
- **M24. Chat example room privacy and whisper addressing.** `authorizeSubscribe()`
  (`ChatHandler.php:98-101`) allows any `room:*` without joining, so a lurker reads a room without
  appearing in its member list (*confirmed*); whispers are addressed by nickname (`chat.js:217`)
  and nicknames are not unique, so an impostor can receive them.

## 4. Low

### Server and runtime
- `THttp2WebSocketProtocol::send()` `:297-317`: output produced by held input fed after the
  captured `$output` is not returned and waits for the next `send()` (*confirmed* at protocol
  level). Loop `_session->send()` after `feedDeferred()`.
- `_deferred` (`:276-289`) is unbounded: PING, SETTINGS, HEADERS and RST are not flow-controlled,
  so the docblock's backpressure claim (`:271-273`) holds for DATA only.
- `receive()` feeds new bytes before leftover held bytes (`:284-285`) — unreachable through the
  server, which drops the session on a throw.
- `serve()` set-up and tear-down are not exception-safe: `cluster->open()` runs after
  `TAsync::setLoop()` outside the `try`, and a throwing `cluster->close()` skips
  `detachReactor()` (*confirmed*: the global loop is left pointing at a dead reactor).
- `serveOnce()` does not install the reactor as the `TAsync` loop; fibers started under a
  host-driven `serveOnce()` loop never resume. Undocumented.
- Per-tick housekeeping (`reapClosingSessions`, `armWrites`, `flushHttp2Output`) is O(sessions).

### Protocol layer
- `close()` sets `_closing` before building the Close frame (`TWebSocketConnection.php:372-373`);
  a 124-byte reason or code 1005 throws and leaves the connection closing with nothing sent
  (*confirmed*). `TWebSocketFrame::close()` (`:107-119`) checks neither reason length nor UTF-8.
- The HTTP/1.1 head parser accepts two `Host` headers (joined), whitespace before the colon,
  obs-fold and `Content-Length` on an upgrade, where RFC 7230 requires 400; `isHostAllowed()` is
  case-sensitive while the Origin check is not (`TWebSocketHandshake.php:141-149`, `:260-267`).
- `buildClientRequest()`, `buildServerResponse()`, `buildRejection()` accept CR/LF in
  caller-supplied host, path and header values.
- Deflate strictness: a stream ending in a BFINAL block without the trailing empty block is
  refused with 1007 (conforming, and asserted by the suite; zlib-based peers accept it); the client
  accepts a response that omits a `server_max_window_bits` it offered (harmless).

### Cluster
- Redis inbox drain is not atomic (`TRedisBackplane.php:198-200` `lRange` then `lTrim`, producers
  trim at `:420`): at the limit, entries can be deleted unread. Wrap in `MULTI`.
- A sender that read `ch:` before a reap can `rPush` after it, recreating an orphan inbox that is
  never reaped.
- Up to `MaxPendingPeers` (64) unverified peers can each buffer `MaxMessageSize` (~640 MiB in all)
  inside the 2 s auth window, with only the replayable handshake proof.
- Docblocks: `IWebSocketBackplane.php:15` and `TNullBackplane.php:20` and README:71 say "Redis
  pub/sub" (it is lists); `IWebSocketBackplane.php:85` says the backplane adds the node id (the
  coordinator does, `TWebSocketCluster.php:134`); `TRedisBackplane.php:40-42`,
  `TMeshBackplane.php:43-51` (see H2, H13, M14).

### Pub/sub, JS client, chat example
- `requestCall()` (`:521-534`) ignores `Allowed`: a guard that sets `setAllowed(false)` on all four
  events blocks subscribe, publish and send but not call.
- `send` to an unknown id still puts a `DIRECT` envelope on the backplane
